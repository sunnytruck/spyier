## ID・文字列・メタデータの取り扱い

- 見出し574件は全て同じ文字列の2連結です。例: 「ストライクストライク」→「ストライク」。原見出しを `sourceNameRaw`、1回分を `sourceName` に保持します。これはカード2枚や別エントリーではありません。
- 同ファイル内の実際の同名重複エントリーは0組です。ファイルをまたぐ同名は職業別の別IDで保存します。「先読み(無色)」と「先読み」は勝手に同一視しません。
- ID は `src_{職業ID}_{SHA-256(NFKC(表示名))の先頭12桁}`。ソースの行番号や効果の調整で変化しません。既存ゲームのカードID・セーブIDは変更しません。真の同名重複が将来入る場合は内容指紋と連番を付け、欠落させません。
- 通常/強化の `costRaw`・`effectRaw` は原文を保持。数値配列・✦連続数は語句解析の観測値であり、実行可能な効果定義ではありません。「✦9」は✦1個の表記と数値9のまま保持し、数値形式へ勝手に直しません。
- カード種別・レアリティの列は全574枚にありません。`type`・`rarity` を `null`、根拠を `not_in_source` とします。プレイ用データで設定する場合は仮設定の根拠を別途明示します。
- 語句の揺れ（例:「弱体」「脱力」「脆弱」、「全て」「すべて」、「6のダメージ」「6ダメージ」、「鍛治師」）は原文に残し、根拠なく置換しません。既存ゲームのweak/vulnerableとの対応はプレイ用実装に明示します。
- `status` は資料の点検状態で、`pending` 493枚、`needs_review` 81枚です。**どちらも取得可・実装済みを意味しません**。戦闘報酬・店・イベントは実行可能な効果定義を持つ別レジストリだけから抽選します。

## 資料だけでは確定できないルール

- XコストはXのまま保存します。エナジー全消費の定義やX+1の扱いはエンジンの明示的なルールが必要です。
- コスト「ー」や強化効果「ー」は原文のままです。0コスト・強化不可・同効果とは断定できません。神託の強化コスト14件もすべて「ー」であり、通常コストから補いません。
- 星を消費するカードへの参照はありますが、資料のコスト欄には星コストの列がありません。星コストを推定して全神託カードを実装済みにしてはいけません。
- オーブの基本数値・スロット数・左右の扱い、オスティの基礎値・被弾順、破滅の判定時点、スライ・リプレイ・プレート等の用語定義は資料にありません。独立した職業ルールの設計・検証が必要です。
- 他プレイヤー・味方参照を含むカードがあり、単独プレイ用の代替対象は未指定です。対象を自分へ読み替えて完了扱いにはしません。
- 「✦」の連続表記と「✦9」などの数値表記が混在します。獲得量が字形から確定するものと、星コスト等の欠落情報を区別します。

## 再生成

添付資料はアプリの実行時依存にせず、入力ファイルをリポジトリへ重複保存しません。元の6ファイルがあるディレクトリを指定してください。

```bash
node scripts/import-card-catalog.mjs --source-dir /path/to/attachments
```

ディレクトリは再帰検索します。同名候補が複数ある場合は取り違えを防ぐため停止します。その場合は6つの `--source 職業ID=/絶対パス/ファイル.txt` を明示できます。出力先は `--out` と `--audit` で変更できます。JSONに現在時刻や実行マシンのパスを埋め込まないため、同じ入力から同じ出力が生成されます。
